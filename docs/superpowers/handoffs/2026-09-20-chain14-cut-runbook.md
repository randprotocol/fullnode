# Runbook: cutting chain 14

Written 2026-09-20 on branch `feat/chain14-cut`, off `origin/main` `a2c9896`. **Nothing in this
file has been run against the fleet.** It is the order of operations for the controller who does.

Chain 14 is the v0.5 chain: the RPL token registry, the bridge with its fixed mainnet guardian set
and emitters, B1–B4's hardening, the hidden-asset bundle, the transaction binding, POOL-1's opened
mint and core I-2's opened alloc notes — and eighteen validator keys that have never been in this
repository (audit v3, OPS-1). Every one of those is a genesis-format or wire change, so this is a
fresh chain, not an update: a chain-13 binary cannot run it and a chain-14 binary cannot run
chain 13.

| | |
|---|---|
| genesis file | `deploy/genesis-chain14.json` (cut once by `deploy/cut-chain14-genesis.sh`, then distributed byte-identically) |
| keys | `$KEYDIR` (default `~/.rand-chain14`), generated by `deploy/gen-chain14-keys.sh`, never committed |
| chain id | 14 |
| call limits | chain 13's five, unchanged |
| aggregation | **none, and not optional** — `node::check_build_runs_genesis` refuses to start on a genesis carrying one |
| faucet | on (a deployer with no balance has to register zUSD) |
| FRI profile | production |
| tokens | `registration_fee` 1 RAND (`1000000000`), `mint_cap_per_day` `10000000000000` (100 000 × 10^8), **no listed token** |
| bridge | guardian **set 0**, emitters for chains 2/3/4/5, six `pq_guardians`, one `pause_key` |
| explorer | randscan `feat/rpl-tokens`, deployed in the same window |

## 0. Before anything

1. **Merge first.** `feat/rpl` and `feat/bridge-hardening` rebase linearly onto `origin/main` and
   fast-forward. No merge commits (user: "so rollback is easier"). This branch, `feat/chain14-cut`,
   rebases on top of that result — its three scripts touch nothing else.
2. **Warn the peer sessions.** `bridge-06` (repo `../bridge`) holds the guardian and relayer side
   and must not rotate the guardian set until the chain is up (`docs/bridge.md` §20 step 6). Any
   session pointing at the chain-13 RPC loses it.
3. **The build sha.** Everything below pins one commit. Call it `$SHA` (`git rev-parse --short
   HEAD` of the merged `main`). One build, fleet-wide: a genesis-format change is a fork and a
   mixed fleet stalls.
4. **Check the PQ public file exists and is the right one.**
   `~/.rand-bridge/mainnet-pq-set1/public.json` — `pq_guardians` (six keys) and `pause_key`, all
   2624 hex characters. It is public-key-only; nothing here ever reads the `*.key.json` beside it.

## 1. NTP on every validator — do this first, not last

B2 makes wall-clock time consensus-relevant for the first time. A block's timestamp may not step
more than `MAX_TIMESTAMP_STEP_MS` = 60 s past its parent (a validity rule, `BlockError::
TimestampLeap`), and no validator votes for a block more than `MAX_CLOCK_DRIFT_MS` = 15 s ahead of
its own clock (a vote rule). A droplet whose clock is 20 s slow silently stops voting; thirteen of
eighteen must vote to commit anything.

On every one of the seventeen droplets:

```bash
timedatectl                     # want: "System clock synchronized: yes", "NTP service: active"
chronyc tracking 2>/dev/null || timedatectl show-timesync --all 2>/dev/null
```

If a droplet is not synchronised: `apt-get install -y chrony && systemctl enable --now chrony`,
then re-check. On node A (the laptop) confirm macOS network time is on. **Do not cut the genesis
until every validator reports synchronised** — the genesis timestamp is the chain's clock zero and
a fleet that disagrees about "now" by more than 15 s never reaches quorum.

## 2. Build on E, at `$SHA`

```bash
# from a clean checkout of the merged main at $SHA
deploy/rebuild-vps.sh 188.166.235.187
```

`rebuild-vps.sh` writes `.git-rev`, rsyncs the tree (`--exclude .git`, `--delete`) and passes
`RAND_BUILD_SHA=$REV` into the remote `cargo build --release -p randprotocol-node -p
randprotocol-client`, because E's `/root/fullnode/.git` is stale and `build.rs`'s own git lookup
would report the wrong commit. Confirm afterwards, on E:

```bash
sha256sum /root/fullnode/target/release/rand-node        # record this; every droplet is checked against it
```

`rebuild-vps.sh` restarts E's `rand-node` on **chain 13** at the end. That is fine — E is cut over
like every other droplet in step 5.

> E must build a tree whose `deploy/` has no key files any more. The rsync is `--delete`, so E's
> copies of `deploy/node-*.key.json` disappear with this build. E's own chain-13 unit points at
> `/root/fullnode/deploy/node-e.key.json` and will fail to restart after the rsync. Either accept
> that (E is minutes from being cut over anyway) or copy E's chain-13 key to `/root/keys/` first
> and repoint its unit. **This is the one ordering trap in the whole run.**

## 3. Generate the eighteen keys — once, off-repo

On the controller's machine, from the repo root, with `target/release/` built locally:

```bash
cargo build --release -p randprotocol-node -p randprotocol-client
deploy/gen-chain14-keys.sh                       # KEYDIR=~/.rand-chain14
```

It writes `node-<name>.key.json` and `payout/<name>.key.json` for
`a b c d e f lon1 sfo3 tor1 blr1 syd1 atl1 ams3 nyc1 nyc2 sfo2 mkc1 mem1` (0700 dir, 0600 files),
runs `refuse_in_tree_key` over every one, and writes the public half:

- `$KEYDIR/public/validators.tsv` — name, address, public key, peer id, payout address;
- `$KEYDIR/public/nodes-chain14.env` — the replacement for `deploy/nodes.env`, same IPs, **new
  peer ids**.

Back the whole `$KEYDIR` up somewhere that is not this laptop before going further. There is no
second copy of a spend key, and eighteen payout wallets are eighteen validators' rewards.

```bash
export KEYDIR=$HOME/.rand-chain14
source $KEYDIR/public/nodes-chain14.env          # NODE_A_PEER, NODE_B … NODE_MEM1
```

## 4. Cut the genesis — and launch within minutes

```bash
NODE=target/release/rand-node WALLET=target/release/rand deploy/cut-chain14-genesis.sh
```

Defaults: `KEYDIR=~/.rand-chain14`, `ALLOC_WALLETS=wallets` (the gitignored `wallets/shielded-{1..5}.key.json`),
`PQ_PUBLIC=~/.rand-bridge/mainnet-pq-set1/public.json`, `OUT=deploy/genesis-chain14.json`.

The script refuses an existing `OUT`, asserts every promise in the finished bytes (faucet, FRI
profile, `hc_bundle` against what this `rand-node` reports, no `aggregation`, eighteen distinct
validators and payouts at 1000 RAND, five alloc notes with openings, the tokens section's fee and
cap with no listed token, six guardians index-aligned with six `pq_guardians`, a separate
`pause_key`, emitters for 2/3/4/5), and prints the **real** chain-14 hash from `rand-node init` —
not the hash `rand-node genesis` printed, which is the unbridged file's.

Record `$GENESIS_HASH` and its first eight characters `$G8`.

> **The clock starts here.** The chain's time begins at this file's `timestamp_ms` and can only
> advance 60 s per block. Cut the genesis when the fleet is ready to start, not the evening
> before: an hour of delay is sixty blocks of a chain whose B1 mint-cap day and guardian-set grace
> window run an hour behind. The script prints the file's age and refuses a timestamp more than
> 15 s in the future.

Commit the genesis file (it is public and must be byte-identical everywhere):

```bash
git add deploy/genesis-chain14.json && git commit
```

## 5. Roll the fleet: C and D first, then the rest, A last

Every node's `--bootstrap` list is built from `nodes-chain14.env`. C and D are the fleet's
bootstraps, so they go first and bootstrap to each other and E.

```bash
export SHA=<the build sha>                       # goes into /root/.update-pin
export G8=<first 8 hex of the chain-14 genesis hash>
export GEN=deploy/genesis-chain14.json
cut() { BOOTSTRAPS="$2" PIN=$SHA KEYDIR=$KEYDIR \
        deploy/cutover-droplet-chain14.sh "$1" "$3" "$G8" "$GEN"; }

# 5a. the bootstraps
cut 164.90.239.200  "$NODE_D $NODE_E" c          # fra1
cut 165.245.173.74  "$NODE_C $NODE_E" d          # ric1

# 5b. the rest, ONE AT A TIME, each waited to rand_getHealth = ok by the script itself
BOOT="$NODE_C $NODE_D"
cut 159.89.185.254  "$BOOT" f                    # nyc3
cut 139.59.160.76   "$BOOT" lon1
cut 24.144.89.22    "$BOOT" sfo3
cut 146.190.243.29  "$BOOT" tor1
cut 167.71.235.108  "$BOOT" blr1
cut 170.64.226.65   "$BOOT" syd1
cut 165.245.142.90  "$BOOT" atl1
cut 146.190.233.230 "$BOOT" ams3
cut 192.81.214.91   "$BOOT" nyc1
cut 107.170.49.234  "$BOOT" nyc2
cut 143.110.135.126 "$BOOT" sfo2
cut 201.79.35.212   "$BOOT" mkc1
cut 168.144.61.10   "$BOOT" mem1
cut 168.144.102.43  "$BOOT" b                    # sgp1, node B's droplet
cut 188.166.235.187 "$BOOT" e                    # sgp1, LAST of the droplets: it serves the explorer

# 5c. node A, the laptop, last of all
```

Each invocation, before it stops anything: copies the genesis and this droplet's key
(`/root/keys/node-<name>.key.json`, 0600, outside `/root/fullnode` so `rebuild-vps.sh`'s
`rsync --delete` can never remove it), pulls the binaries from E and checks their sha256 against
E's, verifies the genesis hash with the new binary, and verifies that the key it just installed is
a validator in that genesis file. Then it stops the service, installs the binaries, inits
`/root/data-$(hostname)-$G8`, backs the old unit up to `/root/rand-node.service.chain13.bak`,
writes a **new** unit (new key path, new datadir, new bootstraps), writes `/root/.update-pin`,
restarts, and waits on `rand_getHealth` = `ok`.

**Nothing commits until thirteen of the eighteen are up.** Expect views to advance and heights to
stay at 0 until the thirteenth node is healthy; that is quorum, not a fault.

Node A (the laptop): update `deploy/run-a.sh` to `BINDIR=bin-$SHA`, `DATA=data-a-$G8`,
`--genesis deploy/genesis-chain14.json`, `--key $KEYDIR/node-a.key.json` and the two chain-14
bootstrap multiaddrs, build `bin-$SHA/` at `$SHA`, then start it. Same for `deploy/run-b.sh` if
the MacBook Air is ever used again — **but node B runs on the sgp1 droplet, and the same validator
key in two places signs two blocks at one height.** Never run both.

## 6. randscan, in the same window

The explorer must be redeployed with the chain-14 fleet, not after it:

```bash
cd ../randscan && git checkout feat/rpl-tokens
deploy/push-to-vps.sh 188.166.235.187 <domain>
```

`feat/rpl-tokens` is not optional. **Every `u64` amount this node's RPC serves is now a decimal
string** — including fields that were JSON integers on chain 13 on purpose: a bundle's `fee`,
`burn_a`/`burn_r`, a mint's / staking action's / `bridge_attest`'s / `bridge_burn`'s `amount`,
`bridge_burn`'s `relayer_fee`, `rand_getAssets`' and `rand_getBridgeState.assets[].locked`, and
`rand_getStatus.aggregation.subsidy_base`. randscan `main` reads several of those as numbers and
renders nothing for them against a live chain 14 (its own mock fixtures were pre-quoted, which is
why this was only caught in review). It also needs the token pages for `rpl1…` ids.

After the deploy, confirm the explorer has re-indexed from genesis and that a token page renders
(there will be no token until step 7).

## 7. Verify, in this order

```bash
q() { curl -s -X POST -H 'content-type: application/json' \
      --data "{\"jsonrpc\":\"2.0\",\"id\":1,\"method\":\"$1\",\"params\":${2:-[]}}" http://$3; }
```

1. **Every node is on the right chain and the right build.** On each droplet:
   `rand status` → `chain_id 14`, `head_hash` present, `active_validator: true`, `faucet: true`,
   `hc_bundle` identical fleet-wide; `rand_getVersion` → `git_sha` = `$SHA`,
   `rand_getGenesisHash` = `$GENESIS_HASH`.
2. **Heights advance.** `rand_getHealth` = `ok` everywhere, and `height` climbing at roughly one
   block per second. Two samples a minute apart on three different droplets.
3. **State roots agree.** Pick a height `H` at least a few behind every node's tip and compare
   `rand_getBlockByHeight [H]`'s `state_root` and block hash across C, E, mem1 and A. They must be
   byte-identical. A divergence here is a fork and everything below stops.
4. **Peers.** `peer_count` 16–17 on each droplet (eighteen validators, one of them the NATed
   laptop).
5. **The faucet works.** `rand faucet <a fresh address>` against E, then
   `rand --key <that wallet> balance` → the minted note appears. This exercises POOL-1's opened
   mint end to end (the ledger recomputes the commitment from `pk`, `time`, `r`).
6. **Bridge state.** `rand_getBridgeState` → `enabled: true`, `guardian_set_index: 0`, six
   `guardians` matching handoff §6 byte for byte, six `pq_guardians`, `pause_key` present,
   `mint_paused: false`, `burn_sequence: 0`, `pause_nonce: 0`, `list_nonce: 0`, `assets: []`,
   emitters for chains 2, 3, 4, 5.
7. **Token registry.** `rand_getTokens` → `enabled: true`, `registration_fee: "1000000000"`,
   `tokens: []`.
8. **A shielded transfer.** One of the five alloc wallets sends to another and the transfer
   commits. This is the first real hidden-asset bundle proof on the chain (~100 s to prove).

Only then hand over to `bridge-06` for `docs/bridge.md` §20 steps 3–7: register zUSD by
transaction, six `ListBacking`, `setToken` on each endpoint **after** the Rand-side listing, then
the guardian-set rotation set 0 → set 1, then the live round trips.

## 8. Rollback

Chain 13 is still there. Nothing in this cut deletes it:

- the chain-13 data dir `/root/data-$(hostname)-8123ccac` is untouched (data dirs are keyed on the
  genesis hash and never collide);
- the chain-13 unit is at `/root/rand-node.service.chain13.bak`;
- `deploy/genesis-chain13.json` is still in the tree;
- the chain-13 key is wherever the old unit pointed — for a–f that was
  `/root/fullnode/deploy/node-<letter>.key.json`, which **`deploy/rebuild-vps.sh` will have
  deleted from E** in step 2 (see the warning there). Keep a copy of every droplet's chain-13 key
  before step 5 if a rollback has to be possible.

To roll one droplet back:

```bash
systemctl stop rand-node
cp -a /root/rand-node.service.chain13.bak /etc/systemd/system/rand-node.service
scp root@<a droplet still on chain 13>:/usr/local/bin/rand-node /usr/local/bin/   # the 86af6eb build
printf '86af6eb\n' > /root/.update-pin
systemctl daemon-reload && systemctl restart rand-node
```

Roll back the whole fleet or none of it — a mixed fleet stalls. If the chain-14 binary has already
opened a chain-13 database, note that **the database is forward-only**: a v0.3+ migration (the
`receipts_by_program` column family) has to be dropped with `rand-node db drop-receipts-index
--datadir <dir>` before an older binary will open it. Chain 14 uses a brand-new data dir, so this
only matters if someone pointed the new binary at the old dir.

## OPEN QUESTIONS

Things this preparation could not settle from the repository. None of them blocks writing the
scripts; each blocks running them without a human answer.

1. **The PQ set is index-aligned with guardian SET 1, but the genesis names SET 0.**
   `~/.rand-bridge/mainnet-pq-set1/public.json`'s own `note` reads: *"Rand chain-14 genesis inputs:
   bridge.pq_guardians (index-aligned with guardian SET 1 = NEW_GUARDIAN1..6) and bridge.pause_key."*
   The genesis, per `docs/bridge.md` §20 step 6, names set 0: *"Only after that: the guardian-set
   rotation (set 0 → set 1, payload 2, signed 5-of-6 by the current set) on the four source
   endpoints, then the same attestation submitted to Rand, whose genesis starts at set 0 (§3)."*
   So at genesis `pq_guardians[i]` and `guardians[i]` are held by *different* operators until the
   rotation lands, and `BridgeConfig`'s own doc comment says "`pq_guardians[i]` belongs to the
   operator of `guardians[i]`", while spec §10 says the relayer "files each co-signature under its
   guardian's ECDSA index". After the rotation to set 1 the two are aligned again (a payload-2
   rotation does not change the PQ set), so this is a transient. **It is harmless only because one
   person currently holds all twelve keys** (handoff §8: "a quorum of 1"). Confirm with bridge-06
   that the relayer will index PQ co-signatures by *PQ list position* and not by the set-0 ECDSA
   signer index during the window between the cut and the rotation — otherwise a mint in that
   window is refused `PqBadSignature`. The script does not guess: it takes the file's array order
   as-is and asserts only length, format, uniqueness and separation of the pause key.
2. **`registration_fee` for chain 14 is not stated anywhere as a chain-14 decision.** The script
   uses `1_000_000_000` (1 RAND) = `genesis::MIN_REGISTRATION_FEE` = the value the nine-phase E2E
   gate runs (`zusd_e2e.rs`'s `REGISTRATION_FEE = UNITS_PER_RAND`). The spec fixes
   `mint_cap_per_day` explicitly and says only "`registration_fee` … set" for the fee. Confirm the
   user wants the minimum; `REGISTRATION_FEE=<units>` overrides.
3. **The alloc wallets are not rotated.** `wallets/shielded-{1..5}.key.json` are gitignored and
   have never been published, so OPS-1 does not reach them — but they have held value on chains
   8–13 and their addresses are in every one of those genesis files. Rotate them too, or keep
   them? The script keeps them (`ALLOC_WALLETS` overrides).
4. **Which key does each regional droplet actually run today, and where?** `deploy/payout/README.md`
   says the `lon1…mem1` name↔droplet pairing is *inferred*, never verified, because a peer id
   cannot be recomputed from a public key. Chain 14 makes this moot going forward — the controller
   *assigns* `node-lon1.key.json` to the lon1 droplet — but it means the chain-13 key path on those
   twelve droplets is unverified. `cutover-droplet-chain14.sh` does not read the old key; confirm
   `grep ExecStart /etc/systemd/system/rand-node.service` on one regional droplet before relying on
   the rollback section.
5. **Node A's and node B's chain-13 keys are the tracked `deploy/node-a.key.json` /
   `node-b.key.json`.** Untracking them leaves the working copies in place, but a *fresh* clone of
   this repository no longer has them. If node A or B ever needs to serve chain 13 again from a new
   checkout, those two files have to be carried over by hand.
6. **`cutover-fleet.sh` has no chain-14 successor.** Step 5's loop is explicit and sequential on
   purpose (each `cut` waits on `rand_getHealth`, so the quorum is never short by more than one),
   but there is no batched wrapper. If a parallel roll is wanted, it needs a script that carries a
   node name and a bootstrap list per droplet — `cutover-fleet.sh`'s `<old> <new>` signature cannot.
7. **The `.update-pin` consumer.** `deploy/README.md` describes it as the MacBook Air's
   auto-updater. B is a droplet now and the Air is offline. `cutover-droplet-chain14.sh` writes the
   pin on every droplet for uniformity; whether anything still reads it, and where that updater
   lives, is not in this repository.
8. **`hc_bundle` for chain 14 is `83d3a370…` on this branch's build** (chain 13's was
   `4a27356f…`), because the hidden-asset guest replaced the bundle guest. The cut script asserts
   the genesis field equals what the building `rand-node` reports, so a mismatched build cannot cut
   a genesis it could not then run — but if the guest changes again between this branch and the
   merged `main`, the number above changes with it. Read it off the cut, do not copy it from here.
9. **`RECURSION_FIXTURES` is still missing on this laptop**, so the ~21 node `--lib` aggregation
   tests remain a known pre-existing failure set. Irrelevant to chain 14 (aggregation is refused at
   startup) but it means "the full suite is green" cannot be claimed here.
