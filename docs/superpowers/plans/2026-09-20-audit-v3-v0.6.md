# Audit v3 remediation, v0.6: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to carry this plan out task by task. Steps use checkbox (`- [ ]`) syntax for
> tracking.

**Goal:** Close every finding from the final security audit v3 that is still open, belongs in this
repository and does not ride the chain-14 cut. Then run the end-to-end suite and tag **v0.6**.

**Architecture:** Four groups, each shippable on its own:
- **A.** Node-only hardening: viewing keys, RPC, witnesses, the wallet, operator nonces, mempool bridge
  checks. No wire, ledger or consensus change; rolls out as a same-chain update.
- **B.** Consensus: the commit rule on the sync path, keeping the lock, f+1 view advance, halting on
  a broken commit path, and a verified-proof cache. No genesis change, but the whole fleet must run
  the same build.
- **C.** Aggregation: the aggregator bound into the aggregate program, the unsealed-fee set under the
  state root, tier gates, the digest pin checked at runtime, the profile check at genesis. A hard fork
  only for a chain with an `aggregation` section, and no chain has one, so live chains are
  unaffected. **Must land before the production proof batch pins `admitted_shapes[0]`.**
- **D.** Process: CI, the version number, negative tests for the bundle guest.

**Tech Stack:** Rust workspace (`randprotocol-core`, `-node`, `-client`, `-zkvm`, `-rvm`), RocksDB,
libp2p 0.57, tokio, axum; the circuits repository (`randprotocol/zkp-circuits`, checked out as
`../circuits`) for the rVM aggregate program.

**Spec:** the audit, `../security/Rand_Final_Audit_v3_Key_Findings.pdf`, 18 Sep 2026, by
https://github.com/zeroknowledge. It carries one-line findings, options and a work order, but no
detailed write-ups. The **Findings verified against code** section below is the working spec: each row
was re-read against `main` at `cba5fef` and against `feat/rpl` on 2026-09-20. Where the audit ID is
ambiguous (CON-3) that is stated.

## Review follow-ups, ruled 2026-09-20 (fullnode-fc's rounds 2 and 3)

Three things the review raised that are **not** fixed on the branches, with the ruling on each:

- **A syncing validator broadcasts a stale vote per block taken through the live path** (~240 after
  a restart a few hundred blocks back). Safe — the vote is for a block that is already committed,
  and no honest replica counts it — but noisy on the wire and in logs. **Accepted noise; a
  follow-up.**
- **A junk above-head batch costs its peer nothing**: `offer_pending` swallows every error, so a
  peer serving rubbish above our head is not dropped the way one serving a bad contiguous batch is.
  **A follow-up.**
- **The above-head route drops `cb.pruned` and the sealed-coverage check.** It hands blocks to the
  live path, which knows nothing about pruned bundles, so a pruned-history batch arriving above the
  committed head would lose its side table. Harmless today because no chain carries an
  `aggregation` section and nothing prunes. **A hard prerequisite before any chain enables
  aggregation** — it belongs with Task C4 and the production proof batch, not after them.

### Task B3: the pacemaker (CH-1, review I1 and I2) — **redesign, not a patch**

**Decided 2026-09-20 (fullnode-fc's independent review, agreed by this session):** the f+1
view-change commit is **lifted out of the chain-14 fleet update** and becomes its own v0.6 piece,
built on timeout certificates.

Why: advancing on f+1 NewViews closes a real halt — one validator's word moved every node up to
`MAX_VIEW_AHEAD` views ahead — but on its own it trades that for a stall that needs no attacker.
The reviewer's pacemaker model (3 s base, 24 s cap, 18 equal stakes) had a rejoining node with no
backoff overrun the converged pack and never be pulled back: 5 of 40 runs stalled permanently with
the threshold at f+1, 3 of 40 at "more than a third", none on main. A backoff patch is not worth
trusting on a chain holding custody. Every attack the lifted commit closes needs a validator key,
and today all eighteen are the operator's.

What the redesign owes:
- a timeout certificate: f+1 signed timeouts for view v, carried on the proposal for v+1, so a
  replica entering a view has evidence rather than a claim;
- `ValidatorSet::has_weak_quorum` as `total − floor(2·total/3)` — f+1, which is 6 of 18, not the
  7 that "more than a third" gives (review I1; a converged pack of 12 sits below the quorum of 13,
  and the difference decides whether it can still move). The function and its test
  `weak_quorum_is_f_plus_one` were lifted with the commit and return here;
- tests at **eighteen** validators, not four: the reviewer's counter-examples all need a set that
  large;
- re-modelling against `av3review/pm.py` before it goes near a fleet.
