# RPC v0.3: the methods Ethereum and Solana clients expect

Design for the fullnode's next tag, `v0.3`, written 2026-09-18 from the RPC comparison in
`docs/rpc-comparison.md`. Thirteen new JSON-RPC methods and two WebSocket topics, all node-only:
no consensus, wire-format or genesis change, so the fleet takes it as a same-chain update
(`deploy/update-droplet.sh`) and chain 12 keeps running.

`rand_feeHistory` is deliberately not here. It needs the fee-ordered mempool, which does not exist
yet, and a history of flat floors would say nothing.

## 1. Goals

This is the fullnode's release; `v0.4` elsewhere in this repository names the Rust toolchain and
the zkVM transpilers, and is unrelated to it.

- Close the gaps a wallet or explorer author hits first: a post-submit status that distinguishes
  pending from dropped, a per-program receipt query, fee-free multi-gets, a health string and a
  build version.
- Keep every read bounded. The node's one unbounded read, `rand_getWitness`, gets a multi-get that
  amortises the tree rebuild rather than a second way to trigger it.
- Change nothing a wallet already relies on. Every existing method, error code and subscription
  keeps its shape.

## 2. Method contracts

Parameters are positional, as every method in `docs/rpc.md`. Hashes, program ids and roots are
hex with an optional `0x`. Errors use the existing codes: `-32602` for a bad parameter, `-32000`
for a refusal, `-32601` for an unknown method.

### 2.1 Node identity

**`rand_getVersion`** — `[]` →
```json
{ "version": "0.1.0", "git_sha": "c66e6b8…", "chain_id": 12,
  "hc_bundle": "f07a…19", "fri_profile": "production" }
```
`version` is the workspace crate version. `git_sha` is the full commit hash, captured at build
time by a `build.rs` in `randprotocol-node`: `git rev-parse HEAD` when the tree is a checkout,
else the `.git-rev` file at the workspace root (the deploy worktrees write it), else `"unknown"`.
A dirty tree appends `-dirty`. The deploy's sha-compare stays on the binary; this method is how
the explorer confirms the fleet from outside.

**`rand_getGenesisHash`** — `[]` → the genesis hash as hex, from the `meta` family. Chain id is
not enough on a project that cuts chains weekly: chain 11 and chain 12 could carry the same id
on a misconfigured node, and this call catches it before a sync is wasted.

**`rand_getHealth`** — `[]` →
```json
{ "status": "ok" }
{ "status": "syncing", "behind": 412 }
{ "status": "behind", "behind": 30 }
```
`ok` when `sync_target - height <= 2` and no batch request is outstanding. `syncing` while one is.
`behind` when the node is not syncing and the lag is above 2, which is the chain-8 stall shape.
A load balancer reads `status` alone; an operator reads `behind`.

### 2.2 Transactions

**`rand_getTransactionStatus`** — `[[hash, …]]`, at most 64 hashes →
```json
[ { "hash": "…", "status": "committed", "height": 1998, "index": 0 },
  { "hash": "…", "status": "pending" },
  { "hash": "…", "status": "rejected", "reason": "nullifier already spent" },
  { "hash": "…", "status": "unknown" } ]
```
Order of lookup per hash: committed (the `txs` family), then pending (the mempool), then rejected
(the admission `RefusedCache`, which holds the `TxError` for every permanent refusal this node
has made), else unknown. A transaction this node never saw and one that was refused by a peer
both read `unknown`; that is honest, and the wallet's submit goes to one node.

The client's `wait_for_transaction` switches to this method so a dropped transaction fails on the
first poll that reads `rejected` rather than at the timeout.

**`rand_subscribe` topic `"transaction"`** — `["transaction", hash]` → one notification when the
hash commits (`{ "status": "committed", "height", "index" }`) or is refused (`{ "status":
"rejected", "reason" }`), after which the node removes the subscription itself. A hash that is
already committed at subscribe time is answered on the next committed block, not synchronously,
so the client has one code path.

### 2.3 Receipts and programs

**`rand_getReceipts`** — `[program_id, from_height, to_height, limit?]` →
```json
{ "receipts": [ { "tx", "program", "tier", "outputs", "height", "index", "h_in" }, … ],
  "next_height": 2051 }
```
Receipts for `program_id` with `from_height <= height <= to_height`, ordered by height then index.
`limit` defaults to and is capped at 256, and a `limit` of 0 is clamped up to 1. `limit` is a soft
floor, not a hard page size: a page never splits a height, so once it holds `limit` receipts it
still serves the rest of that height's matching receipts before it stops. `next_height` is the
first height not served at all — resume from it — or `null` when the page ran out because
`to_height` did, not because `limit` did. The receipt object is exactly `rand_getReceipt`'s.

**`rand_subscribe` topic `"receipts"`** — `["receipts"]` or `["receipts", program_id]` → one
notification per committed block that carries at least one matching receipt:
```json
{ "height": 2051, "hash": "…", "receipts": [ …receipt objects… ] }
```
A block with no matching receipt sends nothing. A filtered subscription with a program id the
node has never seen is accepted, since the program may be deployed later.

### 2.4 Shielded pool

**`rand_getWitnesses`** — `[[index, …]]`, at most 32 indices →
```json
{ "root": "…", "witnesses": [ { "index": 7, "path": ["…", …] }, { "index": 9, "path": null } ] }
```
One `leaves()` read and one `FullTree` build for the whole list. An index past the tree reads
`path: null` rather than failing the call. `rand_getWitness` stays as it is and is implemented as
the one-element case.

### 2.5 Blocks and consensus

**`rand_getBlocks`** — `[from_height, to_height]` → a list of headers, at most 128 (the compact
block cap) from `from_height`, each
```json
{ "height", "hash", "view", "parent", "proposer", "timestamp_ms", "tx_root", "state_root",
  "justify_view", "sealed", "tx_count" }
```
No transactions; `rand_getBlockByHeight` serves those. A range past the head is truncated.

**`rand_getFinality`** — `[height]` or `[hash]` →
```json
{ "status": "committed", "height": 1998, "hash": "…" }
{ "status": "certified", "height": 1999, "hash": "…", "qc_view": 2251 }
{ "status": "proposed", "height": 2000, "hash": "…" }
{ "status": "unknown" }
```
`committed` when the block is at or below the committed head. `certified` when it is in
HotStuff's uncommitted tree and a QC for it exists (`high_qc` or `locked_qc` names it, or a child
carries a `justify` for it). `proposed` when it is in the tree without one. By height, the lookup
is against the committed chain only; an uncommitted height reads `unknown`, since two proposals
may share it.

**`rand_getProposer`** — `[view]` or `[from_view, to_view]`, at most 64 views →
`[ { "view": 2251, "proposer": "2nRdFC…" }, … ]`, the leader under the **current** validator set
(`HotStuff::leader`). Views are not mapped to epochs, so a view from a past epoch reads the
current set's answer; the result says which epoch it used: `{ "epoch": 3, "proposers": […] }`.

**`rand_getMempoolInfo`** — `[]` →
```json
{ "count": 2, "bytes": 2611200, "oldest_ms": 1450, "max_count": 10000 }
```
`bytes` is the sum of `encoded_len`. `oldest_ms` is the age of the longest-pooled transaction, or
`null` when empty. Each `Pooled` entry gains an `Instant` for it.

**`rand_getEmission`** — `[]` →
```json
{ "inflation": "0",
  "subsidy": { "current": "250", "base": "1000", "halving_blocks": 210000,
               "sealed_blocks": 420001, "next_halving_at": 630000 },
  "faucet": true }
```
There is no inflation and the method says so as a fixed `"0"`, so a client that expects Solana's
`getInflationRate` gets a number rather than a missing method. `subsidy` is the block-aggregation
schedule (`gas::subsidy`); on a chain whose genesis has no aggregation section (chain 12) it is
`null`. `faucet` mirrors `rand_status`.

## 3. Storage: the receipts-by-program index

One new column family, `receipts_by_program`, appended to `ALL_CFS`:

- key: `program_id (32) || height (8, big-endian) || index (4, big-endian)`
- value: the transaction hash (32)

Written in the same `WriteBatch` as the receipt (`storage.rs` ~1257) and deleted in the same
truncate pass that drops receipts above the new head (~1691), keyed from the receipt being
dropped. `rand_getReceipts` is one prefix iterator from `program_id || from_height` that stops at
`to_height` or the limit.

**Backfill.** On `Storage::open`, if `receipts_by_program` is empty and `receipts` is not, scan
`receipts` once and write the index in batches of 1 000. Receipts carry `program`, `height` and
`index`, so nothing else is read. Logged at info with the count. On the fleet this is 22 000
receipts at most and takes under a second; on an empty node it is a no-op. A node whose index is
half-written (killed mid-backfill) is not detected; the next open sees a non-empty index and
skips. To make the write atomic enough, the backfill writes a `meta` marker
`receipts_by_program_built = 1` in its last batch and the check is on the marker, not the
emptiness.

## 4. Node plumbing

New `NodeCommand` variants, each a `oneshot` reply like `Peers` and `Epoch`:

- `TxStatus { hashes, reply }` — looks up the mempool and the refused cache; storage is read by the
  RPC layer directly.
- `Finality { key: HeightOrHash, reply }` — reads `HotStuff`'s tree and QCs.
- `Proposer { views, reply }` — `HotStuff::leader` per view plus the current epoch.
- `MempoolInfo { reply }`.

A second broadcast channel next to `heads`, `commits: broadcast::Sender<CommitSummary>`, with
`CommitSummary { height, hash, tx_hashes: Vec<Hash>, receipts: Vec<CallReceipt> }`, sent from the
same place as the head (`node.rs` ~1197), same capacity (`HEAD_CHANNEL`). Refusals are announced
on a third, `refusals: broadcast::Sender<(Hash, String)>`, sent where the refused cache is
inserted. The WebSocket task subscribes to all three; `subs` becomes
`BTreeMap<String, Topic>` with `Topic::{NewHeads, Receipts(Option<ProgramId>),
Transaction(Hash)}`. A lagging receiver on any channel closes the socket, as today.

## 5. Bounds

| what | cap | why |
|---|---|---|
| hashes per `rand_getTransactionStatus` | 64 | 64 storage reads and two map lookups each |
| indices per `rand_getWitnesses` | 32 | one tree build regardless; the cap bounds the reply |
| receipts per `rand_getReceipts` page | 256 | one page is under 100 KB |
| headers per `rand_getBlocks` | 128 | the compact block cap |
| views per `rand_getProposer` | 64 | pure computation, bounds the reply |
| subscriptions per socket | 8 | unchanged, `MAX_WS_SUBSCRIPTIONS` |

## 6. Testing

- `rpc.rs`: one test per method in the existing `call(st, method, params)` harness, plus a cap test
  per bounded method and a `-32602` test per parameter shape.
- `storage.rs`: index round-trip, truncate drops the index rows above the head, backfill fills an
  index from existing receipts and the marker makes the second open a no-op.
- `ws.rs`: `receipts` unfiltered, `receipts` filtered, `transaction` on commit, `transaction` on
  refusal, and the self-removal after delivery.
- `randprotocol-client`: `wait_for_transaction` returns the refusal reason on `rejected`.
- The full `cargo test --workspace` stays green; the node `--lib` aggregation tests that need
  `RECURSION_FIXTURES` are run on E, not the laptop.

## 8. Out of scope

- `rand_feeHistory` (needs the fee-ordered mempool).
- Address-indexed history and event logs (privacy, see `docs/rpc-comparison.md` §2).
- Mapping past views to their epoch's validator set in `rand_getProposer`.
- A mempool-aware `next_nonce` (AGENTS.md open follow-up; separate change).

## 9. Changes during implementation

This spec is a record of the design as written; it is not rewritten to match what shipped.
Where the two differ:

- **The tag is `v0.3`**, decided mid-implementation, not `v0.4` as titled above and throughout
  this document and the plan. Neither document is renamed for it; a later task does that.
- **`rand_getReceipts` paging never splits a height.** `limit` is a soft floor, not a hard page
  size: a page may run past it by the rest of its last height, and `next_height` is the first
  height not served at all, not a cursor mid-height. There is no de-duplicate-by-`tx` note for
  clients, because a page boundary never falls inside one block. A `limit` of 0 is clamped up to
  1 rather than read as "no limit" or refused.
- **`rand_getBlocks` headers carry `justify_view`**, the block's own justify certificate's view,
  which §2.5's field list above omitted.
- **`rand_getProposer` checks the view-count bound before doing any work**, so `[0, u64::MAX]`
  is refused on the count rather than attempting to allocate a `from..=to` range first.
- **The `transaction` topic answers a hash already settled at subscribe time on the next
  committed block**, not synchronously in the subscribe reply — one code path for a client that
  subscribes before or after submitting. `rejected` is exactly what the refused cache holds, the
  same set `rand_getTransactionStatus` reports as rejected; a duplicate submission or a pool
  conflict never reaches that cache, so it is never announced on this topic.
- **A lag closes a socket only when the connection holds a topic the lagging channel feeds.**
  `newHeads`, `receipts` and `transaction` are separate broadcast channels (`heads`, `commits`,
  `refusals`), each with its own 256-slot backlog; a `newHeads`-only client is untouched by a lag
  on the other two.
- **The three subscription streams are independent of each other**, not sequenced against one
  another: a client subscribed to more than one may see block N's `receipts` notification before
  its `newHeads` notification, or the reverse.
- **`randprotocol_client::wait_for_transaction`** calls `rand_getTransactionStatus` and fails
  fast on a `rejected` status; against a node too old for it (`-32601`), it falls back to the
  previous polling loop.
- **First start of a node running this release** builds the `receipts_by_program` index from the
  existing `receipts` family once, as designed in §3; nothing else about that section changed.
