## 2. Gating principle

Chain 14 is live with 36 USDT in custody. Every change lands in one of three classes:

- **node-only** — no wire or rule change; rolls one node at a time like v0.5.1 (§5, §9, §10).
- **wire-coordinated** — a new sync message; an old node ignores it, a new node cannot gather the
  new evidence from old peers, so the fleet rolls whole before the rule has teeth (§4).
- **genesis-gated** — a consensus rule that would fork chain 14 is switched on by a genesis field
  chain 14 does not carry; the node's behaviour on chain 14 is byte-for-byte unchanged, the rule
  activates at the next cut (§3, §6, §7, §8). The pattern is the repo's own (`aggregation`,
  `tokens`): an `Option` field, `skip_serializing_if = "Option::is_none"`, appended to the genesis
  commitment only when present, restored by `reload_ledger` on restart.

Every rule change comes with a regression test that fails on the current code, per the repo's
"verify every test red" rule.

## 3. STAKE-2: the faucet cannot buy the validator set

Today `Action::Mint` (100 RAND, any key in the validator register, no counter) plus an open
`Bond` at `MIN_STAKE` = 1 000 RAND against 18 000 RAND of genesis stake lets one validator key
reach a third of the stake in ~91 mints and two thirds in ~361, active at the next epoch
(1 000 blocks). The node's limiter (burst 8, 1/s) is per process and not consensus.

New optional genesis section:

```json
"staking": { "faucet_budget_per_epoch": "100000000000", "bond_activation_epochs": 2 }
```

Rules, all active only when the section is present:

1. **Faucet ⊕ bridge** (`GenesisError::FaucetWithBridge`): `faucet: true` with a `bridge` section
   is refused by `Genesis::validate`. Chain 14's genesis has both and no `staking` section, so it
   still loads.
2. **Faucet budget per epoch**: the ledger keeps `faucet_epoch: u64` and
   `faucet_minted_in_epoch: u64`; a `Mint` that would push the epoch's total over
   `faucet_budget_per_epoch` is refused (`TxError::FaucetBudgetExhausted`, permanent for that
   epoch — not cached as permanent, since the next epoch admits it again). Both counters are
   consensus state: folded into the state root (domain `rand-state-5`, used only when the section
   is present) and persisted beside `META_SUPPLY`; the replay audit checks them.
3. **Bond activation delay**: a validator entry created by `Bond` records `activation_epoch =
   current_epoch + bond_activation_epochs`; `derive_set` skips entries whose activation epoch is
   in the future. Genesis validators activate at epoch 0. The leaf domain becomes
   `rand-validator-leaf-4` (the activation epoch appended) only when the section is present.

Not in this release: slashing (D8) — "it means nothing while stake is free".

Tests: genesis with faucet + bridge + staking is refused; 101 mints in one epoch against a
100-RAND budget: the 101st refused, the first of the next epoch admitted; a bond in epoch e is not
in the set for epochs e+1..e+N and is at e+N+1; chain 14's genesis (no section) builds to the
pinned hash and the state root domain is unchanged.

## 4. CON-4: the lock is released only on signed evidence, and the locked block is persisted

Today `fallback_high_qc` lowers `locked_qc` to `head_qc` once `fetch_block` has failed
`MAX_FETCH_ATTEMPTS` = 8 times — a "failure" being any connected peer's `Block(None)` or a timeout,
peers chosen by an unsigned `Status`. Eight sybils release any honest validator's lock.

Changes:

1. **The locked block is persisted with the lock.** `Action::PersistSafety` carries the block the
   new `locked_qc` certifies when it is above the head; storage writes it under
   `META_LOCKED_BLOCK` (CF_META, replaced on each advance, deleted when the lock reaches the
   head). `HotStuff::resume` puts it back in the tree, so a restarted validator never has to fetch
   its own locked block. This alone removes the whole-fleet-restart case that motivated the
   fallback.
2. **A signed "not held".** `SyncResponse::NotHeld(NotHeld { hash, signer, signature })` — a
   validator that is asked `BlockByHash(h)` and holds neither the block nor a committed block of
   that hash answers with a Dilithium2 signature over
   `digest_domain(b"rand-not-held-1", genesis_hash ‖ h)`; a non-validator answers `Block(None)`
   as today. The fetcher verifies the signature against the current epoch set and records the
   signer's stake against `h`.
3. **The release rule.** The lock is lowered only when the not-held stake for the locked block is
   **strictly more than a third of the current set's stake** (`ValidatorSet::has_third`) — so at
   least one honest validator is among the signers. Timeouts and `Block(None)` count as attempts
   (bounding the fetch loop) but never as evidence. `high_qc` keeps today's fallback (it is
   liveness state, not a promise). Evidence is cleared when the block arrives or on commit.
4. Old peers never answer `NotHeld`, so in a mixed fleet a lock on an unobtainable block holds
   until the fleet has rolled — accepted (D15). Documented in the roll notes.

Tests: eight `Block(None)` replies no longer lower the lock (fails today); not-held from a third of
the stake does, from less does not; an invalid or off-set signature is ignored; a restarted
validator finds its locked block in the tree without a fetch (fails today); the old
`leader_falls_back_when_high_qc_block_is_unobtainable` keeps the high-QC half only.

## 5. CON-3: sibling proposals are bounded

Today `on_proposal` inserts any leader-signed block with a certified parent, for any view up to
`MAX_VIEW_AHEAD` = 1 000 000 ahead, into a 512-entry tree pruned only on commit; a leader can fill
the tree with siblings and stop every honest proposal (`TreeFull`) until a commit — which needs a
proposal.

Rules (node-only, local acceptance policy — a block refused here is still valid to others):

1. **One block per (view, proposer)**: a second, different block for a view already holding one
   from the same leader is refused (`ConsensusError::Equivocation`) and logged with both hashes.
2. **A proposal window**: a block whose view is more than `PROPOSAL_VIEW_WINDOW` = 8 views ahead of
   the replica's current view is refused (`ConsensusError::ViewTooFarAhead`); views advance on
   QCs and NewViews, not on far-future proposals. (The pacemaker redesign, B3, is unchanged.)
3. **Pruning is not only on commit**: when the tree is full, blocks that neither extend `high_qc`'s
   branch nor sit on the committed head's branch are evicted oldest-view-first before the new
   block is refused, so a certified-branch proposal is always insertable.

Tests: a leader's second block for its view is refused; a proposal 9 views ahead is refused while
one 8 ahead is accepted; 600 sibling proposals do not stop the honest leader's next proposal
(fails today with `TreeFull`).

## 6. The genesis hash in every signed consensus message (consensus domain v1)

Today votes sign `rand-vote ‖ view ‖ hash`, NewViews `rand-newview ‖ view ‖ bincode(high_qc)`,
proposers sign `rand-block ‖ bincode(header)`; none carries the chain. A genesis field
`consensus_domain: u32` (absent = 0 = today) switches every signing message to the `-2` domain
with the genesis hash prepended: `rand-vote-2 ‖ genesis ‖ …`, `rand-newview-2 ‖ genesis ‖ …`,
`rand-block-2 ‖ genesis ‖ bincode(header)`. `Vote::sign/verify`, `NewView::sign/verify`,
`Block::sign/verify` take a `SigningDomain { version, genesis_hash }` from `ConsensusConfig`. The
not-held attestation (§4) is new and always binds the genesis hash.

Tests: a vote signed for chain A does not verify under chain B's domain v1; domain 0 verifies
exactly as before (the existing consensus suite runs under 0 and under 1).

## 7. Bridge: rotation, rolling caps, no listing while paused

All gated on a new optional field group in the genesis bridge section:

```json
"bridge": { …, "rules_v2": { "global_mint_cap_per_window": "500000000000000", "cap_window_secs": 86400 } }
```

1. **`Action::RotatePqGuardians { new_pq_guardians, pq_signatures }`** (variant 22) and
   **`Action::RotatePauseKey { new_pause_key, pq_signatures }`** (23): bundle-less, fee-less
   governance actions under the current PQ quorum, messages
   `rand-bridge-pq-rotate-pq-1 ‖ chain_id ‖ rotation_nonce ‖ len ‖ keys…` and
   `rand-bridge-pq-rotate-pause-1 ‖ chain_id ‖ rotation_nonce ‖ key`; a new `rotation_nonce` on
   `BridgeState` (folded into `rand-bridge-state-5` when `rules_v2` is present). The new PQ set
   must be index-aligned with the ECDSA set (same rule as genesis), have no duplicates, and not
   contain the pause key; the new pause key must not be a PQ guardian. Bincode appends variants,
   so existing encodings are unchanged; an old node refuses the unknown variant at decode, which
   is why these are genesis-gated (`BridgeError::RulesV2Disabled` on chain 14) and never
   submitted before a cut.
2. **Rolling window caps**: each `Backing` keeps a 24-slot ring of `(hour, minted)`; the
   per-backing check sums the slots inside `cap_window_secs` of the block timestamp instead of
   the calendar day; a registry-wide ring enforces `global_mint_cap_per_window` across every
   backing of every token. Rings are state (in the token root under `rand-token-registry-3`, only
   with `rules_v2`). Chain 14 keeps `mint_day` accounting.
3. **Listing refused while paused**: `RegisterBridgedToken` and `ListBacking` are refused with
   `BridgeError::MintsPaused` while `mint_paused` — under `rules_v2` only, since chain 14's
   ledger must keep accepting what it accepts today.
4. `tx_json` renders the two kinds; `rand-bridge-gov` (bridge repo) gains the two signing
   commands later — the message formats are specified here so the CLI can follow.

Tests: a rotation under the old PQ set is refused after a rotation; a pause key that is a PQ
guardian is refused; 2× the cap across a window boundary is refused where the calendar-day rule
admitted it (fails today); the global cap refuses the mint that the per-backing cap admits;
listing while paused refused under `rules_v2`, admitted without.

## 8. TOK-1: a cap on the registry

`tokens.max_tokens: Option<u32>` (genesis; absent = today's `u32::MAX`). `RegisterToken` and
`RegisterBridgedToken` refuse `RegistryFull` at the cap. `rand_getTokens` pages with
`BTreeMap::range(from..)` instead of a scan. The O(tokens) root stays: under a cap of a few
thousand it is bounded work per block, and an incremental root would change the token root
domain for every chain — deferred to the cut that needs it, with the cap as the bound until then.

## 9. OPS-3: disk guard

`node::start` measures free space on the data directory's filesystem (`libc::statvfs`, a direct
dependency now — it is already in the lock file) and refuses to start below
`--min-free-disk-mb` (default 1024) with a message naming the directory and the flag. `NodeStatus`
gains `disk_free_bytes` and `disk_low`; `rand_getHealth` answers `{"status":"disk_low",
"free_bytes":…}` ahead of `ok` when free space is under four times the minimum, and the status
tick logs a warning at that level. Retired-chain data directories are already deleted at cutover
(2026-09-21); the cut runbook keeps that step. Not in this release: pruning `CF_TXS` duplicates.
