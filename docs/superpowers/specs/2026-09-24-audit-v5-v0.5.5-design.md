## 2. OPS-4: the QC stored once

Today `Storage::commit` writes every committed block to `CF_BLOCKS` (its header carries `justify`,
the QC of its parent) and the block's own QC to `CF_QCS`; `verify_chain`, `committed_block`
(sync serving) and `head_qc` read `CF_QCS`. For every committed block but the head, that row equals
the next block's `header.justify`.

- `Storage::commit` writes the new head's QC to `CF_QCS` and deletes the rows of every block the
  batch made non-head (its parent's, and each block's inside the batch but the last). Genesis
  (height 0) keeps its row.
- `qc_by_height(h)`: `h == head` or `h == 0` → the `CF_QCS` row; otherwise `block(h+1).header.justify`
  (a committed child always exists). `verify_chain`'s check `qc.block_hash == hash && qc.view ==
  block.view()` now also proves the parent link, which is stricter, not weaker.
- `truncate_to(h)`: before deleting `h+1..`, write `block(h+1).header.justify` as `h`'s `CF_QCS` row.
- **Migration at open** (`Storage::open`, once, idempotent): if `CF_QCS` holds any row for
  `0 < height < head`, delete them all in one batch and `compact_range_cf(CF_QCS)` — ~250 000
  rows, ~12 GB reclaimed on chain 14; a marker `META_QCS_PRUNED = 1` skips it next time. An old
  build reading a pruned database fails `committed_block` for non-head heights (`Corrupt`), so
  **rollback below v0.5.5 needs a resync** — the release notes say so.
- Numbers for D19: per block after this, `blocks` ≈ 60 KB (the justify inside the header) and
  `qcs` 0 → ≈ 3.6 GB/day at 1.4 s blocks, ≈ 1.7 GB/day at 3 s.

Tests: after committing three blocks `CF_QCS` holds exactly `{0, head}`; `committed_block(h)`
returns the right QC for every `h`; `verify_chain` (Full) passes; `truncate_to` leaves the new head
with a row and serves it; a database written with a row per height is pruned at open and answers
identically; the sync capstone in `tests/cluster.rs` still passes.

## 3. CON-4 per v5: quorum, and durable pending blocks

- `record_not_held` releases the lock only when the attesting stake passes
  `ValidatorSet::has_quorum` (strictly more than two thirds), not `has_third`. Tests move from
  "a third" to "a quorum" (4 of 6 equal stakes releases; 3 does not).
- **Durable pending blocks.** When `update_high_qc` raises the high QC to a block in the tree,
  the replica emits `Action::PersistPending(Vec<Block>)`: the certified chain from the committed
  head's child up to the high QC's block, in order (a few blocks; ≤ 3 in steady state). Storage
  writes it as one bincode value under `META_PENDING_BLOCKS` (replacing the previous); a commit
  emits `PersistPending(vec![])` after `prune`. `HotStuff::resume` takes `pending: Vec<Block>`
  and inserts each through `execute_and_insert` in order (stopping at the first that does not
  extend what it holds), then restores `high_qc`/`locked_qc` from the safety state exactly as
  today. `META_LOCKED_BLOCK` and `restore_locked_block` are subsumed: the locked block is always
  in the certified chain; the key is read once more for a database written by v0.5.4 and then
  deleted.
- With this, a restart never loses the block the persisted high QC names, so the fetch, the
  not-held path and the ghost memory become the exceptional paths they were meant to be.

Tests: a replica restarted after a QC forms on an uncommitted block holds it and its high QC
without a fetch (fails today: the block is gone); the certified chain of two pending blocks is
restored in order; a v0.5.4-shaped database (locked block under the old key, no pending set)
resumes as before; the quorum threshold tests.

## 4. WEB-2 / WEB-3 (website repo)

- **Balance page**: the "spend key" radio and the key-file path are removed; the textarea takes
  the 64-hex viewing key only (`rand viewing-key` prints it), with copy explaining why a spend
  key never belongs in a browser tab. `key_info(text, "viewing")` is the only call.
- **Address page**: generation and download stay (that is the page); the "import a key file or
  spend key to see its address" field is removed.
- **WASM provenance**: both pages fetch the `.wasm` bytes themselves, hash them with
  `crypto.subtle.digest("SHA-256")`, compare with a digest pinned in the page at build time
  (`public/account/viewing/SHA256` and `public/clients/address/SHA256`, written by the two
  `build.sh`), and only then `WebAssembly.instantiate(bytes, imports)` through the glue's init;
  a mismatch refuses with the expected and actual digests on screen. `server/address-wasm/
  build.sh` writes `BUILT_FROM` (the fullnode commit the crate built against) like the viewing
  build already does.

## 5. WEB-5 (sale service, website repo)

`scan_chain` records a transfer as confirmed only when two independent sources agree on `(chain,
tx_hash, log_index, recipient, amount)`: EVM chains query `SALE_RPC_<CHAIN>` and a new
`SALE_RPC_<CHAIN>_2` (defaults: a second public provider) over the same block range and take the
intersection; Tron queries TronGrid and `SALE_TRON_API_2` (a second explorer/API) and takes the
intersection. A transfer seen by one source stays pending (never credited) and is logged. Unit
tests with `FakeHttp`: a transfer on one source only is not credited; on both it is. The binary is
rebuilt with `cargo zigbuild --release --target x86_64-unknown-linux-musl` and installed per
`DEPLOY.md`.

## 6. TOK-2 (gated)

`tokens.burn_registration_fee: Option<bool>` in `TokensConfig`, carried on `RegistryExt`
(committed to the genesis hash by name only when present, like `max_tokens`). Under it, for
`RegisterToken` and `RegisterBridgedToken` the ledger keeps `fee − registration_fee` for the
proposer and adds `registration_fee` to `supply.burned` (no note is created for it); the
proposer therefore pays the registration fee like anyone else. Not on chain 14.

## 7. Release hygiene

- The WAL-cap test polls (done, `efa0a00`): the v0.5.4 tag's CI failure was a mid-flush read.
- `deploy/retire-chain-dirs.sh <ip>`: deletes every `data-*` directory on a droplet whose genesis
  suffix is not the one in the unit's `ExecStart`, only when `rand_getHealth` is `ok`; the cut
  runbook calls it after the cutover.
- The release notes carry a capacity statement: bytes per block measured after §2, days a 48 GB
  and an 80 GB droplet last from the current usage.

## 8. After this release: the deep scan

Per the user's goal: an adversarial multi-reviewer pass (consensus safety and liveness under
Byzantine leaders and restarts; ledger arithmetic and supply conservation; the hidden-asset
guest and the zkVM's soundness assumptions; the bridge's quorum and cap logic; the paper's
claims against the code, including the Poseidon2 constants question ZKV-2 raises), each finding
verified against source and fixed with a red-first test. Its own spec follows this release.
