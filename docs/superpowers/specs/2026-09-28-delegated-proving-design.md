# Delegated proving: a prover service, and split authorisation — design

Status: draft 2026-09-28, written from a conversation in the clients repo; **not reviewed, not
built**. Read against `origin/main` at `aedf458` (v0.6).
Scope: fullnode (this repo). Companion: `../clients/docs/superpowers/specs/2026-09-28-delegated-proving-design.md`.
Ships in: Phase 1 on any chain (no consensus change). Phase 2 is a hard fork, genesis-gated, and
waits for the measurements in §3.6.

Update 2026-09-29: Phase 1 shipped as v0.6.2; Phase 2 is built on `feat/delegated-proving-2` for
v0.6.3 (plan `docs/superpowers/plans/2026-09-28-delegated-proving-phase2.md`). The text below is
the design as drafted; where the build differs it is marked here (§4.2's measurements, §5's table
and its last paragraph). The user-facing description of the code is `docs/prover.md`,
`docs/shielded.md` §2 and `docs/confidential.md`.

## 1. Problem

A bundle proof is tier 14: about 100 s and 5.7 GB on a laptop CPU. A browser gives WebAssembly
4 GiB, and most phones have less than 8 GB, so the extension, the web wallet and most mobile
devices cannot send or withdraw at all. The owner wants wallets split into **light clients** and a
**prover** that runs elsewhere — its own binary, or a mode of a full node — with the rule that
someone who wants full privacy runs their own.

That gives the chain three paid or payable roles:

| role | does | hardware | paid by | defined in |
|---|---|---|---|---|
| validator (proposer) | orders transactions, verifies proofs | CPU | the fee's verification share | `docs/staking.md` |
| aggregator | one recursive proof over many bundles | GPU | the fee's proving share + the block subsidy | `docs/aggregation.md` |
| **delegated prover** | one bundle proof for one sender | 8 GB+ CPU, or GPU | that sender, privately (§4) | this spec |

## 2. The obstacle: the witness carries the spend key

`hidden::hidden_bundle_inputs` writes `sk` into the private-input vector (`hidden_input::SK`), and
the guest derives `nk` and `pk_self` from it. Knowledge of `sk` is the only thing that authorises
a spend. So on every chain up to 15, whoever receives a prove request can build any other
transaction for that wallet: **delegating a proof is handing over custody.**

Hence two phases:

| | prover receives | prover can read | prover can spend | who may run it |
|---|---|---|---|---|
| Phase 1 (today's guest) | `sk` | the wallet's whole history | **yes** | the wallet's owner only |
| Phase 2 (split authorisation) | `nk` | the wallet's whole history | no | anyone |

Phase 2 does not make delegation private. `nk` is the viewing key: it derives the ML-KEM
decapsulation key and `ovk`, so a prover that proved one transaction can read everything that
wallet ever received or sent, before and after. That is the trade the owner named; the clients
must say it in those words.

## 3. Phase 1 — the prover service (no consensus change)

### 3.1 Where it lives

- A new crate `crates/randprotocol-prover`: the wire types, the sealed-payload codec, the job
  queue and an axum service. The clients vendor this repo, so they get the same types.
- A binary `rand-prover` (that crate's `main.rs`): the service alone, no chain state.
- `rand-node run --prover <ADDR>`: the same service inside a node process, on **its own listener**.
  It is never a method of the public RPC (`rpc.rs` authenticates nobody, by design).

Proving goes through `prove_bundle_for(hc, profile, inputs, binding, backend)`, unchanged. The
service holds no keys of any wallet and never sees a transaction: only the witness words and the
eight binding words.

### 3.2 Wire protocol

JSON-RPC 2.0 over HTTP POST, the node's own conventions, namespace `prover_`:

| method | params | result |
|---|---|---|
| `prover_info` | — | `{version, kem_fingerprint, hc_bundles[], profiles[], backend, witness_kinds[], queue: {depth, max}, fee}` |
| `prover_submit` | `sealed_hex` | `{job}` — 128 random bits, hex |
| `prover_status` | `job` | `{state, position?, reply?, error?}`; `state` ∈ `queued｜proving｜done｜failed｜expired` |
| `prover_cancel` | `job` | `{cancelled}` |

The job and the reply are sealed end to end, so TLS termination at a proxy reveals nothing:

```
sealed  = kem_ct (1 088 B) ‖ nonce (12 B) ‖ ChaCha20-Poly1305(key, postcard(ProveJob))
key     = blake3::derive_key("rand-prover-request-1", ml_kem_768_shared_secret)

ProveJob   { version: 1, token: [u8; 32], witness_kind: SpendKey | ViewingKey,
             hc_bundle: Word8, profile: FriProfile,
             binding: [u32; TX_BINDING_WORDS], inputs: Vec<u32>, reply_key: [u8; 32] }
ProveReply { proof: Vec<u8>, digest: Word8, tier: u8 }     // sealed under reply_key, fresh nonce
```

These are the primitives envelopes already use (ML-KEM-768, ChaCha20-Poly1305), so the wasm core
needs nothing new. `reply_key` is 32 fresh random bytes per job.

### 3.3 Pairing and authentication

The prover's identity is its ML-KEM-768 key, generated by `rand-prover keygen` (mode 0600, like
`node.key.json`). `rand-prover pair --name <LABEL>` mints a 32-byte token, stores its hash, and
prints a pairing link, also as a QR code:

```
randprover:<base58(kem_ek)>?url=<https URL>&token=<hex>&own=1
```

- A job whose token is unknown is refused before it is queued. `rand-prover unpair <LABEL>` revokes.
- `own=1` marks a prover the wallet's owner runs. **A client sends a `SpendKey` witness only to
  a prover paired with `own=1`.**
- A prover started without `--accept-spend-key` refuses `SpendKey` jobs, and says so in
  `prover_info.witness_kinds`. The flag is off by default.

### 3.4 Resource control

- `--max-parallel` (default 1) proofs at once; `--max-queue` (default 8) waiting; a full queue
  answers `busy` with the depth.
- At start, refuse to run if the machine has less than `PROVER_PEAK × max-parallel + 1 GiB` free.
- A job not collected within 10 minutes of `done` is dropped (`expired`).
- `--backend cpu|cuda`, as the `Backend` enum allows in this build.

### 3.5 Witness hygiene

- The witness lives in memory only, in a zeroize-on-drop buffer; it is never written to disk,
  logged, or included in an error. Logs carry the job id, the token's label, the tier and the time.
- The decrypted job is dropped as soon as the proof exists or fails.
- A test records everything the service logs and returns and scans it for the witness's `sk`
  words, as the clients' `assertKeyNeverLeaked` does.

### 3.6 What the client checks on the reply

The prover is not trusted for correctness. The client recomputes the expected digest before it
submits (`hidden_bundle_digest`), refuses a reply whose digest differs or whose proof exceeds the
chain's `max_proof_bytes`, and verifies the proof locally where the shell can. A tainted witness
still proves (the guest sets `bad`), so digest equality is the check that matters.

## 4. Phase 2 — split authorisation (hard fork)

### 4.1 Construction

The spend key moves out of the bundle guest into a second, tiny proof the light client makes
itself:

```
auth guest        private: sk, salt        nk = H(NK, sk);  c = H(AUTH, nk, salt)
                  publishes c              proved against the transaction's binding

bundle guest v3   private: nk, salt, the rest as today
                  pk_self = H(PK, nk);  c = H(AUTH, nk, salt)
                  digest  = H(…today's fields…, c, bad)
```

- `Bundle` gains `auth_commit: Word8` (the public `c`) and `auth_proof: Vec<u8>`.
  `Transaction::binding` blanks both proofs.
- The ledger verifies the auth proof against the binding it recomputes and requires its output to
  equal `auth_commit`; the bundle digest it recomputes includes `auth_commit`.
- A prover holding `nk` can prove the bundle but cannot produce an auth proof for it. An auth
  proof is bound to one transaction's binding, so it cannot be replayed onto another.
- `salt` is 256 fresh random bits per transaction. A repeated salt repeats `c` and links two
  transactions to one wallet; the guest cannot enforce freshness, so the wallet does, and a test
  asserts it.
- **Addresses, keys and existing notes do not change.** `pk = H(PK, nk)` stays as it is.
- One shape for every transaction: a wallet that proves for itself makes both proofs. A
  self-proved and a delegated transaction are indistinguishable on chain.

The guest computes `c` with the plain `POSEIDON2` syscall (not constraint set 7's `POSEIDON2_LEN`) over
a fixed 17-word preimage `[AUTH, nk, salt]`, like every note-layer hash, so it is `auth::auth_commit`
bit for bit and costs one fixed-length hash.

Genesis selects it the way `hc_bundle` selects v1 or v2 today: a new `hc_bundle` for v3 and a new
`hc_auth` pinning the auth guest.

The size is the real cost. Phase 2 therefore ships only when **one** of these holds, decided from
a spike (task P2-0): aggregation is active on the target chain; the auth proof measures small
enough to keep two transfers per block; or the owners accept the throughput. **Decided
2026-09-28:** the owners accept the throughput — the user ordered Phase 2 executed and the chain
cut; the cost, until aggregation is active, is one transfer per 4 MiB of block.
A v3 transaction carries three proofs at most (bundle, auth, call), so a genesis that sets
`hc_auth` must give `max_block_bytes ≥ 3·max_proof_bytes + 1 MiB` (`gas::min_block_bytes`; refused
at `Genesis::validate` otherwise, the defaults included): a 4 MiB block admits transfers but no
`Call` at Production FRI (bundle 1.49 MB + auth 1.36 MB + a tier-10 call proof ≈ 4.22 MB), and
chain 17 is cut with 4 MiB proofs in 20 MiB blocks.

### 4.3 Rejected

| option | why not |
|---|---|
| a signature verified inside the bundle guest (WOTS/XMSS) | hundreds of extra permutations against 235 of headroom: tier 16, about 400 s and 21 GB; changes `pk`, so every address changes |
| a re-randomisable signature key, as Sapling's `rk` | needs a homomorphic key; no standard post-quantum scheme has one |
| Dilithium2 outside the circuit, key revealed | the revealed key links every spend of a wallet |
| an optional auth proof (delegated transactions only) | marks delegated transactions publicly and splits the anonymity set |
| trusted hardware, or multi-party proving | a different trust model; out of scope |

### 4.4 Soundness review

Before it ships, a cheating suite with real proofs, each case accepted if the check were missing:
an auth proof for a different `nk`; for a different binding; a bundle whose `c` uses a different
`salt` than the auth proof; `auth_commit` in the bundle differing from either proof; an auth proof
replayed from another transaction; and Task 5b's binding tests on both guests.

## 5. Fees for a delegated prover

**Yes, a separate incentive — paid by the sender, inside the same bundle, as a shielded RAND note.**
No consensus change, no new field, no subsidy.

- `prover_info.fee` quotes a flat amount in RAND units and the prover's shielded address.
- The wallet adds one RAND output paying it. The prover sees every output in the witness, checks
  that one names its `pk` with at least the quoted amount, and refuses the job otherwise.
- It is atomic: the prover is paid only if the transaction it proved is committed.
- It is invisible: on chain it is one more commitment among the four.

Where the output fits in the 4-in/4-out shape:

| transaction | asset slots 0–1 (outputs) | RAND slots 2–3 (outputs) |
|---|---|---|
| token transfer | payment, change | **prover fee**, RAND change |
| BridgeBurn / TokenBurn | dummy, change | **prover fee**, RAND change |
| RAND transfer (`A = 0`) | **prover fee**, change | payment, change |
| RAND bundle paying nobody (`A = 0`: a bond, a deploy, a call, a bridge action) | dummy, dummy | **prover fee**, RAND change |

As built (`Plan::outputs`, `crates/randprotocol-client/src/wallet.rs`): the burn row's asset slots
are (dummy, change) — slot 0 is the payment slot, empty for a burn — where this table first read
(change, dummy); the RAND bundle that pays nobody was not in the draft and puts the fee in slot 2.
The prover accepts the fee in any RAND slot (slots 2–3 always, 0–1 when `A = 0`), so neither
choice is a wire rule.

A RAND transfer funds the fee from a RAND input in slots 0–1, so a wallet holding a single RAND
note must split it first (one self-transfer).

As built, the prover checks the fee **output** in the witness but not the envelope sealed to it,
which the witness does not carry: a wallet can pay the note and seal junk, so neither side can
open it. That is griefing only — the RAND is lost to both. Follow-up: the prover keeps the fee
note's opening from the witness. The wallet caps what it pays with `--max-prover-fee` (default
1 RAND) and does not remember the quote it saw at pairing.

Why not the alternatives:

- **No subsidy.** A delegated proof is indistinguishable from a self-made one, so a subsidy would
  be claimable by anyone proving their own transactions.
- **No public `prover_fee` field** (the `relayer_fee` pattern): it would mark delegated
  transactions.

The remaining risk is a client that takes the proof and never submits, or spends the inputs
elsewhere first. In Phase 2 the client sends the whole unproven transaction and its auth proof, so
the prover assembles and broadcasts it itself; a race still costs the prover one proof, which the
pairing token's rate limit bounds. Phase 1 provers are the owner's own and charge nothing.

**Deferred — not built in v0.6.3.** The paragraph above is not what the build does: the prover
receives only the witness and the binding words (`ProveJob`), never the transaction, and the
client assembles and submits the transaction itself, as in Phase 1. So the risk stands as stated —
a client can take the proof and not submit, and the prover has done one unpaid proof, bounded by
the pairing's per-token cap (`--per-token`, default 2 jobs at once).

## 6. Relation to aggregators

Both need the same hardware, so an aggregator operator is the natural delegated prover.
`docs/aggregation.md` §2's forward path already sends bundles sender → aggregator; with Phase 2 a
sender can hand the same operator the witness instead of a finished proof. Nothing here couples
the roles in the protocol.

## 7. Tasks

Phase 1: P1-1 the crate, wire types and sealed codec · P1-2 the queue and service, `rand-prover` ·
P1-3 `rand-node run --prover` · P1-4 pairing, tokens, `--accept-spend-key` · P1-5 the hygiene test
and an end-to-end test (a job proved remotely is admitted by a node) · P1-6 `docs/prover.md`.

Phase 2: P2-0 the spike (auth guest size and time, natively, in wasm, on a phone; v3 headroom) ·
P2-1 the two guests and their layouts · P2-2 the cheating suite and its review · P2-3 core
(`Bundle`, binding, ledger) · P2-4 node (RPC `tx_json`, genesis `hc_auth`, mempool) · P2-5 client
and CLI · P2-6 the prover fee check.

## 8. Open questions

1. Does Phase 2 wait for aggregation, or is one transfer per block acceptable for a testnet cut?
2. Should the ML-KEM decapsulation key derive from `sk` rather than `nk` on a later cut, so a
   prover holding `nk` cannot decrypt notes it was never shown? It changes every address.
3. Is `rand-node run --prover` wanted at all, or only the separate binary? A validator that also
   holds witnesses is a larger target.
4. Pairing over a LAN needs TLS a browser accepts; is that the operator's problem, or does the
   desktop app carry a relay?
